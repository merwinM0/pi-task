# 任务进度报告约定（可合并到现有 AGENTS.md）

对需要多个执行步骤的工作使用 `pi-task` 报告状态；简单问答不必创建清单。

1. 先确认 `pi-task` 可用；不可用时告知用户，不自动安装、不阻塞正常工作。
2. 允许先做少量只读检查，然后在主要修改/执行之前确定清单。按可验收的工作阶段拆解，不把每个工具调用都变成一步。
3. 用一次 `pi-task start --title "简短标题" --task "第一步" --task "第二步" ...` 提交整份清单。若步骤很多，可通过 `--file -` 从标准输入提交 JSON 字符串数组。文本只记录状态，不放入密码、密钥或其他敏感内容。
4. 记住 start 返回的工作 ID。后续每次写入明确传入 `--id ID`；不要依赖不同 Bash 工具调用之间共享 shell 变量，不要把“最近一次工作”当成写入目标。
5. 开始某一步：`pi-task update --id ID --task 1 --state running`。
6. 验证某一步已完成后再标记 done；需要测试的步骤应以实际测试结果为依据。可用 `--note "验证依据"` 附简短说明。
7. 可以合并两个状态变化以减少工具开销：`pi-task update --id ID --task 1 --state done --next 2`。不要反复提交整份清单，不要为动画或耗时轮询 status。
8. 新发现的工作用 `pi-task add --id ID --text "新步骤"` 增补；修订标题用 update 的 `--text`，阻塞用 `--state blocked --note "原因"`。不要覆盖已有进度，不要冒称任务总数永远不会变化。
9. 全部步骤验收并标记 done 后执行 `pi-task finish --id ID`。失败或用户取消时，能报告则使用 `finish --state failed` 或 `finish --state cancelled`；不要把未完成步骤自动打勾。
10. 更新命令失败时不要假装面板已更新；修正参数、重试一次或向用户说明。监看器本身不执行、检查或证明工作已完成。
11. 任务状态更新可以与实际工作命令放在同一次 Bash 调用里，但正确保留真实工作命令的退出码；不要用 `; ... done` 无条件宣布成功。
12. 只有用户需要人工查看时才建议运行 `pi-task`；不要在代理工具里启动交互查看器，它会持续等待键盘输入。

以上命令是通用 CLI 形式。若在 fish 中手动保存 ID，使用 `set -l run_id (pi-task start ...)`，不是 Bash 的 `run_id=$(...)`。代理的 Bash 工具可以使用 Bash 语法，但变量不保证跨工具调用保留。
